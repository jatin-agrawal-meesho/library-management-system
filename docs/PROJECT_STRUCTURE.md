# PROJECT_STRUCTURE

> Why every file, folder, and package exists. Java/Maven projects follow a strict **standard layout**
> ("convention over configuration") so every project looks the same and tools work without setup.
> **Phase 2** adds the layered application packages (controller/service/repository/entity/config),
> PostgreSQL + Redis, and a `docker-compose.yml` to run them.

## The Maven Standard Directory Layout — why this exact shape

Maven mandates `src/main/...` and `src/test/...`. The split exists because **application code and test
code have different lifecycles**: test code (and test-only dependencies, scope `test`) must be compiled
and run during the build but **never shipped** in the final jar.

| Path | Role | Maven meaning |
|------|------|---------------|
| `src/main/java` | Production source code | Compiled into the jar |
| `src/main/resources` | Production non-code files (config) | Copied onto the classpath, into the jar |
| `src/test/java` | Test source code | Compiled & run during `mvn test`, **not** shipped |
| `target/` | Everything Maven generates | Compiled `.class` files, the jar, etc. |

> `src/main/resources` ends up on the **classpath** — that is *why* Spring Boot finds
> `application.properties` automatically at runtime.

## Why the code is split into packages (controller/service/repository/entity/config)

This is **layered architecture** — each package is one responsibility, and dependencies point in one
direction (top calls down, never up):

```
   controller  ──calls──►  service  ──calls──►  repository ──►  PostgreSQL
   (HTTP)                   (logic +             (data access)
                            cache)  ──uses──►  RedisTemplate ──►  Redis
        every layer uses the  entity  (Book) as the data it passes around
        config  wires up beans (RedisTemplate) that the layers consume
```

Grouping **by layer** (not by feature) is the most common, beginner-friendly Spring convention. It maps
cleanly onto how you'd structure an Express app (routes → controllers → services → models), the
difference being that Spring's IoC container instantiates and wires these for you (see `FUNDAMENTALS.md` §3, §8).

**Why all packages live under `com.meesho.library`:** `@SpringBootApplication` starts a component scan
rooted at its own package. Every class annotated `@RestController` / `@Service` / `@Configuration`
(and every `@Entity` / repository interface) is auto-discovered **only because it sits in a sub-package
of the base package.** Move a class outside `com.meesho.library` and Spring would silently never find it.

## File-by-file rationale

### `docker-compose.yml` — local infrastructure
Declares two containers the app connects to as a **client**: PostgreSQL (`:5432`, db/user/pass all
`library`) and Redis (`:6379`). Not Java, not seen by Spring — it just makes the two servers exist so
the connection settings in `application.properties` have something to connect to. `docker compose up -d`
starts both; `docker compose down` stops them. Postgres has a named volume (data persists); Redis does
not (a cache is disposable). See `FUNDAMENTALS.md` §11–§12.

### `pom.xml`
The build descriptor. Phase 2 adds three dependencies: `spring-boot-starter-data-jpa` (JPA + Hibernate +
connection pool + Spring Data), the `postgresql` JDBC driver (scope `runtime`), and
`spring-boot-starter-data-redis` (Lettuce client + `RedisTemplate`). See `LEARNING_NOTES.md`.

### `LibraryManagementApplication.java`
Unchanged from Phase 1: the single entry point (`main` + `@SpringBootApplication`). It triggers the
component scan that discovers everything below.

### `entity/Book.java`  — the data
A POJO annotated `@Entity` that Hibernate maps to the `books` table (fields `id`, `title`, `author`).
Used as the in-memory representation everywhere: request body, response body, repository return type,
and Redis cache value. Not a Spring bean (one object per row, not one shared instance). See
`FUNDAMENTALS.md` §9–§10.

### `repository/BookRepository.java`  — data access
An **empty interface** extending `JpaRepository<Book, Long>`. Spring Data JPA generates the
implementation (a proxy with all CRUD SQL) at startup and registers it as a bean. The only place that
touches PostgreSQL. See `FUNDAMENTALS.md` §10 and `LEARNING_NOTES.md`.

### `config/RedisConfig.java`  — wiring
`@Configuration` class with one `@Bean` method that builds a customized `RedisTemplate<String, Book>`
(string keys, JSON values) so cached data is human-readable in `redis-cli`. The bean it returns is
injected into `BookService`. See `FUNDAMENTALS.md` §12.

### `service/BookService.java`  — business logic + caching
`@Service` bean that owns the **cache-aside** logic for `getById` (check Redis → fall back to Postgres →
populate Redis) and cache eviction on delete. Holds the `CACHE HIT` / `CACHE MISS` log lines. Depends on
`BookRepository` and `RedisTemplate`, both injected via its constructor. The heart of Phase 2. See
`FUNDAMENTALS.md` §13 and `REQUEST_FLOW.md` §3–§4.

### `controller/BookController.java`  — HTTP layer
`@RestController` mapping the four endpoints (`POST/GET/GET{id}/DELETE`) to methods that delegate to
`BookService`. Handles JSON binding (`@RequestBody`), path variables (`@PathVariable`), and status codes
(`@ResponseStatus`). No business logic. See `REQUEST_FLOW.md`.

### `src/main/resources/application.properties`
Externalized config. Phase 2 adds the PostgreSQL datasource URL/credentials, JPA/Hibernate settings
(`ddl-auto=update`, `show-sql=true`), the Redis host/port, and a logging level so the cache logs show.
See `FUNDAMENTALS.md` §6.

### `target/` — build output (do not edit, do not commit)
Generated by Maven (compiled classes, the executable fat jar). Disposable; `mvn clean` deletes it.

## How the pieces interact (Phase 2)

```
                                  HTTP (JSON)
                                      │
        ┌─────────────────────────────┼──────────────────────────────────┐
        │  Spring Boot app (one JVM process, embedded Tomcat :8080)        │
        │                             ▼                                    │
        │                     BookController                               │
        │                             │                                    │
        │                       BookService ──────────────┐                │
        │                             │                    │                │
        │                       BookRepository       RedisTemplate          │
        │                       (Hibernate/JDBC)     (Lettuce client)       │
        └─────────────┬───────────────────────────────────┬───────────────┘
                      │ SQL over :5432                      │ GET/SET over :6379
                      ▼                                     ▼
              ┌───────────────┐                     ┌───────────────┐
              │  PostgreSQL    │  (docker)           │     Redis      │  (docker)
              │  table "books" │   source of truth   │  key "book:id" │   cache
              └───────────────┘                     └───────────────┘
```

- **Build/run path** (from Phase 1, unchanged): `pom.xml` → Maven compiles `src/main/java` + bundles
  `resources` → `target/…jar` → `main()` → `SpringApplication.run()` → component scan wires all beans →
  Tomcat listens on :8080.
- **Request path** (new): see `REQUEST_FLOW.md` for the step-by-step trace of each endpoint.
